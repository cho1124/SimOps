# Workshop-0001: 전체 배포 단위

상태: 사용자 결정 대기

연결 ADR: [ADR-0002: 모듈형 모놀리스와 기술 스택](../decisions/0002-modular-monolith-stack.md)

## 결정할 문제

SimOps의 Backend, 장시간 작업, Dashboard를 어떤 배포 단위로 구성할 것인가?

## 현재 요구사항

- 개인 프로젝트로 완주 가능해야 한다.
- Run 검증과 랭킹 갱신에 트랜잭션이 필요하다.
- 합성 시뮬레이션은 CPU 사용량이 크다.
- 백엔드와 운영 설계 역량을 보여줘야 한다.
- 향후 기능을 분리할 수 있어야 한다.
- 인프라 구축이 프로젝트의 중심이 되어서는 안 된다.

## 선택지 A: 모듈형 모놀리스 + 별도 Worker

```text
Dashboard
    ↓
하나의 Backend API
├─ Run
├─ Ranking
├─ Config
├─ Experiment
└─ Analytics

별도 Worker
├─ 시뮬레이션
├─ Run 검증
├─ 집계
└─ AI 분석

공용 PostgreSQL
```

### 장점

- 기능 경계를 코드로 구분하면서 배포는 단순하게 유지할 수 있다.
- DB 트랜잭션을 사용하기 쉽다.
- CPU 작업을 API 프로세스와 격리할 수 있다.
- 필요하면 이후 모듈 단위로 분리할 수 있다.

### 단점

- 모듈별 독립 배포가 불가능하다.
- API와 Worker가 DB와 일부 코드를 공유한다.
- 경계를 지키지 않으면 큰 모놀리스로 변할 수 있다.

## 선택지 B: 마이크로서비스

```text
Run Service
Ranking Service
Experiment Service
Config Service
Analytics Service
Simulation Workers
```

### 장점

- 서비스별 독립 배포와 확장이 가능하다.
- 장애와 책임 경계를 프로세스 수준에서 분리할 수 있다.
- 분산 시스템 경험을 깊게 얻을 수 있다.

### 단점

- 인증, 서비스 통신, 메시지 전달, 분산 추적이 필요하다.
- Run 검증과 랭킹 갱신의 일관성 처리가 복잡해진다.
- 로컬 실행과 배포 비용이 커진다.
- 핵심 LiveOps 실험보다 인프라 작업이 커질 가능성이 높다.

## 선택지 C: 단일 프로세스 모놀리스

```text
API + Dashboard + Background Job
        ↓
    PostgreSQL
```

### 장점

- 가장 빠르고 단순하게 구현할 수 있다.
- 디버깅과 배포가 쉽다.
- 초기 기능 검증에 유리하다.

### 단점

- 시뮬레이션이 API 응답성에 영향을 줄 수 있다.
- 웹 요청과 장시간 작업의 생명주기가 섞인다.
- 비동기 처리와 장애 복구 역량을 보여주기 어렵다.
- 이후 Worker 분리가 필요할 가능성이 크다.

## Codex의 추천

선택지 A인 `모듈형 모놀리스 + 별도 Worker`를 추천한다.

프로젝트 완주 가능성을 유지하면서도 시스템 경계, 비동기 처리, 장애 복구, 배포 단위에 대한 판단을 충분히 보여줄 수 있기 때문이다.

이 추천은 최종 결정이 아니다. 프로젝트 소유자가 아래 형식으로 선택 이유와 감수할 비용을 설명하고, 반례 검토 또는 Spike를 거친 후 ADR을 승인한다.

## 프로젝트 소유자 답변

```text
선택:

현재 프로젝트에서 가장 중요한 제약:

다른 선택지보다 적합하다고 판단한 이유:

감수할 단점:

어떤 조건에서 다시 검토할 것인지:

직접 검증하고 싶은 부분:
```

## 후속 검토

답변 이후 다음을 진행한다.

1. 선택 이유에 대한 반례와 실패 시나리오 검토
2. 필요한 경우 최소 Spike 정의
3. ADR-0002의 결정과 결과 갱신
4. 프로젝트 소유자의 최종 승인
