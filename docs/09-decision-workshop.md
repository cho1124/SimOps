# 기술 의사결정 워크숍

상태: 확정

## 목적

SimOps의 기술을 유행이나 추천만으로 선택하지 않는다. 각 시스템의 요구사항과 제약을 기준으로 후보를 비교하고, 프로젝트 소유자가 선택 이유와 포기한 것을 직접 설명한 뒤 ADR로 승인한다.

## 역할

### Codex

- 결정해야 할 문제와 선행 조건을 정리한다.
- 현실적인 후보 2~4개를 제시한다.
- 후보별 장점, 비용, 실패 조건을 동일한 기준으로 비교한다.
- 추천안이 있으면 추천 이유를 밝힌다.
- 사용자의 선택 이유에 반례와 운영 상황을 제시한다.
- 필요한 경우 작은 기술 검증 Spike를 설계한다.
- 합의된 내용을 ADR과 설계 문서에 반영한다.

### 프로젝트 소유자

- 후보 중 하나를 선택한다.
- 프로젝트 요구사항에 근거해 선택 이유를 설명한다.
- 선택으로 포기하는 장점과 감수하는 위험을 설명한다.
- 어떤 조건에서 선택을 재검토할지 정한다.
- Spike 결과를 보고 최종 승인하거나 선택을 변경한다.

## 한 결정의 진행 순서

```text
1. 문제 정의
2. 변경 불가능한 요구사항 확인
3. 후보 2~4개 비교
4. Codex 추천과 근거
5. 프로젝트 소유자의 선택과 설명
6. Codex의 반례·실패 시나리오 검토
7. 필요하면 최소 Spike 실행
8. ADR 승인
9. 다음 의존 결정으로 이동
```

## 선택 설명 형식

```text
선택:

선택 이유:
- 현재 프로젝트에서 가장 중요한 제약
- 다른 후보보다 유리한 점

감수하는 단점:

재검토 조건:

직접 검증할 것:
```

다음 설명은 충분하지 않다.

- 많이 사용하니까
- 최신 기술이니까
- Codex가 추천했으니까
- 확장성이 좋아 보이니까

해당 선택이 SimOps의 규모, 데이터, 실패 방식, 학습 목표와 어떻게 연결되는지를 설명해야 한다.

## 평가 기준

모든 후보는 필요한 항목만 골라 같은 기준으로 비교한다.

- 요구사항 적합성
- 구현 복잡도
- 운영 복잡도
- 재현성과 테스트 용이성
- 장애 격리와 복구
- 성능과 확장 경로
- 보안과 신뢰 경계
- 기존 Unity/C# 역량 활용
- 새로 얻는 학습 가치
- 포트폴리오 설명력
- 교체 비용

## Spike 원칙

문서만으로 판단하기 어려울 때는 제품 기능이 아니라 위험 하나를 검증하는 최소 코드를 작성한다.

예:

- 같은 시드와 행동으로 Unity와 .NET의 result hash가 일치하는가?
- 후보 DB가 랭킹과 실험 집계 쿼리를 충분히 단순하게 처리하는가?
- Worker가 처리 중 종료되어도 Job이 중복 결과 없이 복구되는가?
- Dashboard가 대량 Experiment Cell을 원하는 시간 안에 렌더링하는가?

Spike에는 질문, 성공 기준, 제한 시간, 결과, 결정 영향이 있어야 한다.

## 결정 순서

의존성이 큰 것부터 진행한다.

1. 전체 배포 단위: 모듈형 모놀리스, 마이크로서비스, 단일 풀스택
2. Game Core 공유 방식과 결정론 경계
3. Backend 언어와 프레임워크
4. 영속 저장소
5. 비동기 Job과 Simulation 실행 방식
6. API 스타일과 계약
7. 인간 Run 검증과 인증
8. 분석·집계 방식
9. 운영 Dashboard
10. AI 분석 통합 방식
11. 관측성
12. 배포·호스팅과 CI/CD

앞 결정이 바뀌면 의존하는 ADR을 다시 검토한다.

## 완료 조건

- 주요 기술 선택마다 승인된 ADR이 있다.
- 프로젝트 소유자가 각 선택의 이유와 단점을 설명할 수 있다.
- 위험이 큰 선택은 Spike 결과가 연결돼 있다.
- ADR마다 재검토 조건이 있다.
- 설계 문서와 실제 구현이 일치한다.
