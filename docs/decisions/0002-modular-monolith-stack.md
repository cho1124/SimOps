# ADR-0002: 전체 배포 단위

상태: 승인

결정일: 2026-08-27

연결 워크숍: [Workshop-0001](../workshops/0001-deployment-unit.md)

## 맥락

SimOps는 플레이 API, 랭킹, 설정, 실험, 분석과 CPU 집약적인 시뮬레이션을 필요로 한다. 개인 프로젝트의 완주 가능성을 유지하면서 책임과 장애 경계를 정해야 한다.

## 고려한 선택지

- 모듈형 모놀리스 API + 별도 Worker
- 기능별 마이크로서비스
- API, Dashboard, Background Job을 포함한 단일 프로세스

## 결정

모듈형 모놀리스 API와 별도 Worker를 사용한다.

Backend 언어, DB, Dashboard, Job 기술은 이 ADR의 결정 범위에서 제외하고 각 워크숍과 ADR에서 선택한다.

## 이유

- 기능 경계를 코드로 구분하면서 배포 복잡도를 제한할 수 있다.
- CPU Simulation을 API 요청 처리와 격리할 수 있다.
- 실제 독립 확장 요구가 생기면 모듈을 분리할 수 있다.

## 결과와 포기한 것

얻는 것:

- Simulation, Run 검증, 집계, AI 분석을 API 요청 생명주기 밖에서 처리한다.
- API와 Worker의 프로세스·재시작·동시성·확장 정책을 분리한다.
- API 내부는 모듈 경계를 유지하면서 분산 통신과 분산 트랜잭션을 피한다.

감수하는 것:

- Run, Ranking, Config 같은 API 내부 모듈은 개별 배포·확장이 불가능하다.
- API와 Worker가 코드와 PostgreSQL을 공유하므로 완전한 장애·자원 격리는 아니다.
- Worker의 DB 연결·쓰기·Lock 부하가 API 응답성에 영향을 줄 수 있다.
- 경계를 지키지 않으면 큰 모놀리스로 퇴화할 수 있다.

## 재검토 조건

- 특정 모듈의 독립 배포·확장이 지속적으로 필요함
- API와 Worker의 공유 저장소가 장애 격리를 방해함
- 단일 API 배포가 서로 다른 기능의 릴리스 주기를 막음
- 특정 모듈에 독립적인 보안·소유권 경계가 반복적으로 요구됨

프로젝트나 코드의 크기만으로 마이크로서비스로 전환하지 않는다. 독립성이 필요한 모듈부터 단계적으로 추출하며, 공유 DB를 그대로 둔 프로세스 분리만으로 병목이 해결된다고 가정하지 않는다.

## 검증 의무

- 18,000 Run 처리 중 API latency와 오류율 측정
- Worker 강제 종료 후 Job 유실·중복 결과 0건
- API·Worker의 CPU, 메모리, DB connection, slow query와 Lock 경합 관측
