# 시스템 기획

상태: 확정

## 1. 기준 게임 개요

작업명: `SimOps Arena`

- 장르: 적의 다음 행동이 공개되는 턴제 미니 로그라이크
- 한 Run: 일반 전투 5회와 보스 전투 1회
- 전투 사이: 후보 3개 중 보상 1개 선택
- 종료 조건: 보스 클리어 또는 플레이어 사망
- 사람 기준 목표 플레이 시간: 8~12분
- 시뮬레이션 기준: 그래픽 없이 동일 규칙을 고속 실행
- 클라이언트: 하나의 Unity 프로젝트에서 PC와 모바일 플랫폼군 지원
- 경쟁: 시즌 기반 비동기 랭킹

기준 게임은 SimOps의 실험·운영 기능을 증명할 만큼의 전략적 선택을 제공하되, 콘텐츠 제작이 플랫폼 개발보다 커지지 않게 제한한다.

## 2. 핵심 플레이 루프

```text
활성 시즌과 캐릭터 확인
→ 공개 설정을 내려받아 Run 시작
→ 적의 의도 관찰
→ 2 AP로 행동 선택
→ 적 행동 해결
→ 전투 종료까지 턴 반복
→ 보상 3개 중 1개 선택
→ 다음 전투
→ 보스 클리어 또는 사망
→ 행동 로그 제출
→ 서버 재실행 검증
→ 점수와 인간 랭킹 반영
```

합성 플레이어는 같은 루프를 사용하지만 공개 랭킹에 참여하지 않고 실험과 벤치마크 데이터로만 저장된다.

## 3. Run 구성

| 구간 | 내용 | 목적 |
|---|---|---|
| Stage 1 | 기본 적 | 행동과 적 의도 이해 |
| Stage 2 | 공격형 또는 방어형 적 | 초기 빌드 방향 확인 |
| Stage 3 | 중간 난도 상승 | 누적 난도 곡선의 중간 관찰 지점 |
| Stage 4 | 조합 적 또는 강화 적 | 빌드 적응력 확인 |
| Stage 5 | 준보스급 적 | 완성된 빌드 검증 |
| Stage 6 | 보스 | Run 최종 평가 |

Stage 1~5 종료 후 보상을 제공한다. 보스 종료 후에는 점수만 계산한다.

## 4. 전투 규칙

### 4.1 전투 상태

플레이어:

- 현재·최대 체력
- 공격력
- 기본 방어량
- AP
- 스킬 재사용 대기시간
- 아이템 충전 수
- 현재 Block
- 상태 효과
- 획득한 보상 목록

적:

- 현재·최대 체력
- 공격력
- 현재 Block
- 다음 행동 Intent
- 상태 효과
- 행동 패턴 상태

Run:

- 현재 Stage와 턴
- 누적 턴
- 설정·점수 규칙 버전
- 난수 시드와 서브시드
- 행동·보상 선택 기록
- 현재 점수 구성 요소

### 4.2 턴 순서

```text
1. Turn Start
   - 플레이어 AP를 2로 회복
   - 적의 이번 턴 Intent를 공개

2. Player Phase
   - 유효 행동을 AP가 허용하는 동안 선택
   - 플레이어가 End Turn을 선택하거나 AP가 0이면 종료

3. Enemy Phase
   - 공개된 Intent 실행

4. Turn End
   - Block 초기화
   - 상태 효과와 재사용 대기시간 갱신
   - 사망·전투 종료 판정
```

플레이어와 합성 에이전트는 동일한 관찰 정보를 받는다. 에이전트에만 숨은 게임 상태를 제공하지 않는다.

### 4.3 기본 행동

| 행동 | AP | 기본 효과 | 제한 |
|---|---:|---|---|
| Strike | 1 | 공격력 기반 단일 피해 | 없음 |
| Guard | 1 | 이번 턴 Block 획득 | 턴 종료 시 남은 Block 제거 |
| Technique | 2 | 강한 피해 또는 캐릭터 고유 효과 | 재사용 대기시간 적용 |
| Use Item | 0 | 제한된 회복 또는 유틸리티 효과 | 충전 수 소비, 턴당 1회 |
| End Turn | 남은 AP | 플레이어 Phase 종료 | 항상 가능 |

정확한 수치는 `GameConfig`에 포함하고 코드에 고정하지 않는다. 기본 행동의 의미와 처리 순서는 게임 버전에 속한다.

### 4.4 적 Intent

MVP의 Intent 종류:

- Attack: 일반 피해
- Heavy Attack: 높은 피해, 낮은 빈도 또는 준비 조건
- Guard: Block 획득
- Empower: 이후 공격 강화

적은 유형별로 Intent 상태 머신과 가중치를 가진다. 모든 무작위 선택은 시드 기반이다.

## 5. 성장과 보상

### 5.1 제공 규칙

- 일반 전투 종료 후 활성 보상 풀에서 서로 다른 후보 3개를 제공한다.
- 플레이어는 반드시 하나를 선택한다.
- 후보 생성과 선택은 모두 기록한다.
- 출현 가중치와 효과 수치는 설정으로 변경할 수 있다.
- 보상의 구조적 효과는 게임 버전에 포함한다.

### 5.2 보상 계열

| 계열 | 목표 | 예시 효과 |
|---|---|---|
| Offense | 빠른 처치 | 공격력, 연속 공격, 처형 효과 |
| Defense | 피해 안정화 | Guard 강화, 보호막, 반격 |
| Sustain | Run 생존 | 최대 체력, 전투 후 회복, 아이템 충전 |
| Tactics | 행동 효율 | Technique 강화, 재사용 대기시간, 조건부 AP 효과 |

MVP는 계열별 최소 3개, 총 12개 보상을 목표로 한다. 동일 보상의 중첩 가능 여부와 최대 중첩은 보상 정의에 포함한다.

### 5.3 빌드 다양성 목표

- 어느 계열도 모든 페르소나에서 항상 최선이 되어서는 안 된다.
- 선택지 하나가 전체 선택의 과반을 지속적으로 차지하면 이상 후보로 표시한다.
- 상위 인간 Run과 합성 Run의 보상 조합 분포를 비교할 수 있어야 한다.

## 6. 적과 캐릭터 범위

### 6.1 MVP 플레이어 캐릭터

MVP는 한 캐릭터로 제한한다.

이유:

- 캐릭터 차이보다 합성 페르소나와 설정 차이를 먼저 검증한다.
- 실험 Cell 수와 밸런스 변수를 통제한다.
- Game Core, 데이터, 운영 폐루프 개발에 집중한다.

두 번째 캐릭터는 MVP 이후 교차 캐릭터 밸런스 실험으로 추가한다.

### 6.2 MVP 적

- Striker: 공격 중심
- Guardian: Guard와 지연 전투 중심
- Charger: Heavy Attack 준비와 대응 중심
- Boss: 위 Intent를 조합한 단계형 패턴

Stage별 적 유형과 수치 배율은 설정으로 관리한다.

## 7. 합성 플레이어

### 7.1 공통 규칙

- 모든 에이전트는 같은 `GameObservation`과 유효 행동 목록을 받는다.
- 에이전트의 선택에는 유형, 버전, 파라미터, 난수 시드를 기록한다.
- 에이전트 성향은 실제 인간 세그먼트가 아니라 실험용 행동 모델이다.
- MVP에서는 규칙·효용 기반 정책을 사용하고 LLM이나 강화학습은 제외한다.

### 7.2 MVP 페르소나

| 유형 | 의사결정 특성 | 실험 역할 |
|---|---|---|
| Random | 유효 행동과 보상 중 무작위 선택 | 최저 기준과 예외 탐색 |
| Novice | Intent를 가끔 무시하고 단기 선택, 제한된 실수 확률 | 비효율적 플레이의 난도 관찰 |
| Aggressive | 예상 피해와 공격 보상에 높은 가중치 | 유리 대포형 빌드 관찰 |
| Defensive | 피해 방지, 회복, 생존 보상에 높은 가중치 | 안정형 빌드와 장기전 관찰 |
| Greedy | 현재 관찰에서 1턴 기대 효용 최대화 | 단기 최적화 기준선 |
| Explorer | 덜 선택한 행동과 보상에 탐색 보너스 | 빌드 다양성과 경계 탐색 |

MVP 완료 조건은 다섯 종류 이상이며, Random을 포함한 여섯 유형 구현을 기본안으로 한다.

### 7.3 정책 모델

규칙 기반 에이전트는 후보 행동마다 효용을 계산한다.

```text
utility =
  damageWeight × expectedDamage
  + defenseWeight × expectedPreventedDamage
  + sustainWeight × expectedHealing
  + tempoWeight × actionEfficiency
  + noveltyWeight × explorationBonus
  + seededNoise
```

페르소나는 가중치, 관찰 제한, 실수 확률, 탐색 강도로 구분한다. 정책과 파라미터가 바뀌면 `AgentVersion`을 올린다.

## 8. 점수 시스템

### 8.1 설계 원칙

- 가장 중요한 기준은 진행도다.
- 고의로 전투를 늘리거나 피해를 반복 생성해 점수를 파밍할 수 없어야 한다.
- 같은 시즌에는 하나의 점수 규칙만 사용한다.
- 점수는 클라이언트가 아니라 검증기가 계산한다.

### 8.2 점수 공식 v1 초안

```text
Progress Score = 클리어한 Stage × 10,000
Boss Bonus     = 보스 클리어 시 20,000
Survival Bonus = Run 종료 시 체력 비율 × 5,000
Tempo Bonus    = 각 전투의 max(0, Par Turn - Used Turn) × 100

Final Score = Progress + Boss + Survival + Tempo
```

처치 수와 가한 피해는 점수에 직접 포함하지 않는다. 고정된 Run에서 중복 보상이나 지연 전투로 점수를 파밍하는 것을 줄이기 위해서다.

정확한 Par Turn과 반올림 규칙은 초기 플레이테스트 후 `ScoreRuleVersion 1.0.0`에서 확정한다.

### 8.3 동점 규칙

1. Final Score가 높은 Run
2. 클리어한 Stage가 많은 Run
3. 총 사용 턴이 적은 Run
4. 종료 시 체력 비율이 높은 Run
5. 먼저 검증된 Run

## 9. 시즌과 랭킹

### 9.1 공개 랭킹

- 인간 플레이어의 검증된 최고 Run만 등록한다.
- 합성 플레이어는 공개 인간 랭킹에서 제외한다.
- 전체 상위, 내 주변, 내 최고 기록을 제공한다.
- MVP는 전 세계 단일 랭킹만 제공하고 친구·지역 랭킹은 제외한다.

### 9.2 시즌 공정성

한 시즌은 다음을 고정한다.

- Game Version
- Published Config Version
- Score Rule Version
- 시작·종료 시각

MVP에서 인간 플레이어에게는 시즌의 단일 공개 설정만 제공한다. 합성 플레이어용 Treatment를 인간에게 동시에 A/B 배정하지 않는다.

큰 밸런스 변경은 새 시즌으로 배포한다. 긴급 롤백이 발생하면 해당 설정에서 생성된 기록의 처리 정책을 감사 이력에 남긴다.

### 9.3 기록 검증

```text
클라이언트가 Run 시작 토큰 요청
→ 서버가 season/config/seed를 고정
→ 클라이언트가 플레이 후 순서화된 행동 로그 제출
→ 서버가 같은 Game Core로 재실행
→ 결과 해시와 규칙 위반 확인
→ 점수 계산
→ 검증 성공 시 개인 최고 기록과 랭킹 갱신
```

MVP의 검증기는 활성 Game Version만 지원한다. 종료된 시즌은 최종 순위를 동결한다.

## 10. LiveOps 설정

### 10.1 설정으로 변경 가능한 값

| 범주 | 예시 |
|---|---|
| Player | 초기 체력, 공격력, 방어량, 아이템 충전 |
| Action | Strike 배율, Guard 수치, Technique 배율·쿨다운 |
| Enemy | 기본 수치, Stage 배율, Intent 가중치 |
| Reward | 활성 여부, 출현 가중치, 효과 수치 |
| Encounter | Stage별 적 구성, Par Turn |
| Experiment | Variant 연결, 시드 집합, 페르소나 구성 |

게임 규칙의 구조를 바꾸는 항목은 설정이 아니라 새 Game Version으로 배포한다.

### 10.2 설정 불변성

- 저장된 설정 버전의 내용은 수정하지 않는다.
- 변경은 이전 설정을 부모로 하는 새 버전을 생성한다.
- 배포는 특정 버전을 활성 포인터로 지정한다.
- 롤백은 이전 설정 버전을 다시 활성화한다.

### 10.3 설정 생명주기

```text
Draft → Validated → Simulated → Approved → Published → Retired
                                      ↑          ↓
                                      └── Rollback
```

- Draft: 작성 중
- Validated: 스키마와 값 범위 검증 통과
- Simulated: 필수 합성 실험 완료
- Approved: 운영자 승인
- Published: 인간 플레이에 활성화
- Retired: 더 이상 신규 Run에 사용하지 않음

## 11. 운영자 흐름

```text
1. 문제와 가설 작성
2. Control과 Treatment 설정 선택
3. 에이전트·반복 수·시드 정책 선택
4. 실험 실행
5. 결과와 가드레일 확인
6. 대표 실패 Run 리플레이
7. AI 분석과 다음 실험안 검토
8. 설정 승인 또는 폐기
9. 새 시즌 또는 설정으로 배포
10. 인간 데이터 관찰 및 필요 시 롤백
```

AI는 5~7단계만 지원하며 8~10단계의 권한을 갖지 않는다.

## 12. 플레이어 흐름

```text
익명 계정과 닉네임 생성
→ 활성 시즌 조회
→ Run 시작
→ 게임 플레이
→ 행동 로그 제출
→ 검증 결과 확인
→ 개인 최고 기록과 랭킹 확인
→ 상위 또는 자신의 Run 리플레이
```

## 13. MVP 포함 범위

- 한 캐릭터
- 적 3종과 보스 1종
- 6개 Stage
- 2 AP 턴 전투와 공개 Intent
- 계열별 3개 이상의 보상
- 규칙 기반 합성 플레이어 6종 기본안
- Control과 두 Treatment의 paired simulation
- Headless 대량 실행
- 텔레메트리와 운영 대시보드
- 익명 사용자와 시즌 인간 랭킹
- 행동 로그 기반 서버 재실행 검증
- 근거 지표 기반 AI 결과 요약
- 설정 검증, 승인, 배포, 롤백
- 최소 한 종류의 PC 빌드와 한 종류의 모바일 빌드
- 공통 게임 규칙·콘텐츠와 플랫폼별 입력·레이아웃·생명주기 Adapter

## 14. MVP 제외 범위

- 실시간 멀티플레이
- 여러 플레이어 캐릭터
- 실시간 액션과 물리 기반 입력
- 결제, 광고, 재화 경제
- 친구, 길드, 채팅
- 인간 대상 동시 A/B 배정
- LLM 플레이어와 강화학습
- 무승인 자동 배포
- 장기 리텐션과 매출 예측
- 모든 PC·모바일 운영체제와 스토어 동시 출시

## 15. 수치 기획 원칙

초기 수치는 구현 전에 별도 `baseline-config.json`으로 작성한다. 시스템 문서는 규칙과 조정 가능한 레버를 정의하고, 실제 수치는 다음 과정을 따른다.

```text
손 계산 가능한 기준값 작성
→ Greedy/Random 기준 시뮬레이션
→ 사람 플레이 확인
→ 첫 Control 고정
→ 첫 실험 시작
```
